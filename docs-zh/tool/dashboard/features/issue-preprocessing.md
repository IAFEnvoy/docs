自动预处理会为新增 Issue 创建 AI 会话，阅读问题描述与本地源码，判断问题是否存在并给出解决方案。**只生成报告，不修改项目代码，也不执行构建或测试。**

## 启用

1. 在 [config.yml](../configuration/config-yml.md) 启用 GitHub 数据源，为仓库所有者在 [auth.yml](../configuration/auth-yml.md) 配置 GitHub Token。
2. 在 [ai.yml](../configuration/ai-yml.md) 配置可用的默认模型。
3. 将项目源码放在 `project_paths` 中某个目录下的 `<仓库名>` 子目录中。预处理要求本地源码已存在，缺少目录时会记录失败，**不会自动克隆**。
4. 登录网站，打开 **Agent → 设置**，开启 **自动预处理 Issue**。设置标签位于 **MCP 服务器** 右侧，开关默认关闭。

读取开关、修改开关、查看任务状态和重试均需要有效的登录凭据。开关立即生效并持久保存；关闭后不启动新任务，已运行的任务会完成。

## 哪些 Issue 会触发处理

GitHub 列表按 `server.cache_ttl_minutes` 与各仓库当前缓存到期时间刷新。**成功从上游拉取列表后**才进行差量比较；后台分析顺序执行，不阻塞列表刷新。

| 事件 | 行为 |
| --- | --- |
| 每次重启后某仓库首次成功拉取 | 仅校准基线，不触发预处理 |
| 后续 TTL 刷新 | 只加入相对已观察基线新增、仍为 Open、所属项目未归档的 Issue |
| 登录后清除 GitHub 缓存或全部缓存 | 立即触发重新拉取，沿用同样的增量规则 |
| 缓存命中或上游请求失败 | 不消耗首次保护；失败不推进基线 |
| 编辑、重新打开旧 Issue，或重复刷新 | 不重复派发 |
| 关闭预处理期间成功获取列表 | 更新基线，之后开启不会补扫这些历史项 |

PR 不参与自动预处理。内部按仓库已观察到的最大 Issue 编号识别新增项，并保留已有任务与报告；清除缓存不会清除这些记录，也不会重置首次保护。

**每次重启都适用首次拉取保护，即使磁盘已经保存缓存和基线。** 因此停机期间新增、已出现在重启后首次列表中的 Issue 也只记入基线，从下一次成功拉取开始识别新增项。

例如，上次列表已有 `#100`，刷新后出现新的 Open Issue `#101`，则派发 `#101`；再清一次缓存不会重跑它。重启后首次列表中的 `#102` 只校准基线，下一次才新增的 `#103` 才会触发处理。

## 报告与重试

自动派发与手动点击派发按钮一样创建会话并附带 Issue 正文，固定使用内置的 `issue-preprocessor` 助手。报告包含：

- 问题概述：预期行为、实际行为、触发条件和受影响版本。
- 真实性结论：已确认存在、较可能存在、未发现依据、信息不足或功能请求。
- 证据与根因：引用源码文件、行号和日志，说明推断及缺失信息。
- 解决方案：建议修改位置、步骤、兼容性与风险。
- 验证计划：供维护者执行的复现和回归检查。

在 Issue 旁点击 **查看报告**，或从 AI 对话历史打开对应会话。失败任务可在开关开启时手动重试；重启中断的运行任务会标记为失败。已排队任务持久保存，由新增任务、显式重试或配置变更等事件唤醒处理器。

服务端限制预处理助手为读取、搜索和参考资料获取；修改文件、Shell、外部 MCP 与子 Agent 均不可用，开启审批绕过也不会放宽这些权限。报告中的验证计划不表示系统已经运行过测试。

## 接口与存储

以下接口都需要网站登录：

| 接口 | 方法 | 请求与用途 |
| --- | --- | --- |
| `/api/admin/issue-preprocess` | GET | 读取开关和任务状态 |
| `/api/admin/issue-preprocess` | PUT | `{"enabled": true}`，修改开关 |
| `/api/admin/issue-preprocess` | POST | `{"repo": "owner/repo", "number": 101}`，仅重试已失败任务 |

开关、各仓库基线及任务索引保存在 `data/issue-preprocess.json`，完整报告保存在 `data/sessions.db`。需要将报告发送到 QQ 时，另行配置 [Bot 通知](./bot-notifications.md)；通知开关与预处理开关分别管理。
