## 26.1.2 API adaptation

This time the target dependency source JARs were checked directly, extracted to `build/ftbsrc/26.1.2.8`, `build/ftblibsrc/26.1.2.9` and `build/auisrc/26.1-1.2.6`; the Minecraft signatures were confirmed from the actual 26.1.2 JAR.

- **Server instance**: the target's `ServerQuestFile.getInstance()` returns a non-null instance rather than an Optional; the new entry point checks `exists()` first and does not keep the Optional calls from the source code that do not apply.
- **Native events**: master's NeoForge `FTBQuestsEvent` and `ProgressEventData / ProgressType` are kept, and the Architectury events are not brought over. ClearFileCache locates the bridge by ServerQuestFile and also invalidates the guide generation.
- **Claim order**: normal rewards are still handed to TeamData.claimReward. The target Reward.claim returns void and there is no tryClaim; choice rewards strictly follow the target ClaimChoiceRewardMessage, calling claim on the selected reward after a successful markRewardAsClaimed, and finally checking only the native claimed flag — it does not claim that the third party actually delivered the reward and offers no rollback guarantee.
- **Reward data**: the target writeData accepts a Json5Object, reads xp / xp_levels / random_bonus / only_one with Json5Util, and does not use the 1.21 CompoundTag. Item previews use the vanilla immutable ItemStackTemplate and merge by item and component equality.
- **Text decoding**: a JSON Component is read through ComponentSerialization.CODEC and the registry JsonOps; when it cannot be parsed the literal is kept, and the FTB client text helper classes are not loaded.
- **Client drawing**: the target type uses getIcon, and the Icon renderer records render state into GuiGraphicsExtractor. The new FtbQuestIconRenderer runs in the AUI BODY phase, replaying geometry, text and items into the current AUI output target, transform and projection and reusing the active scissor; it does not call the full GuiRenderer, which would reset the target. Tooltips use setTooltipForNextFrame. There is no old GuiGraphics / flush code and no global GL depth recovery code.
- **Block icon depth**: replaying an item model uses `Base.getGuiItemModelZ()` and cannot reuse Z=0 from 2D icons; the backward part of the model intersects the card background and looks as if faces were culled. The vanilla model culling rules are kept, and the item buffer is submitted before GUI lighting is restored; text such as counts is drawn after the model, using `Base.getGuiItemDecorationZ()` to keep the foreground layer.
- **Commands and naming**: the native Commands.hasPermission is used; public resource IDs use Identifier. Optional FTB classes stay isolated in compat.ftb, the dedicated server does not reference the client icon implementation, and optional classes are not loaded when FTB is not installed.

### 2026-10-31 speech ledger background processing (1.21.1 pending sync)

The user reported a brief freeze after clicking the lottery that then recovered, with no speech exception in the logs. ## 2026-11-07 runtime lifecycle cleanup (1.21.1 pending sync)

AssistantServer becomes a single volatile INSTANCE that is published after the server has finished starting and is cleared before shutdown; the object-identity check in get(server) is kept, and no fields are attached to MinecraftServer and no Mixin is added. FTB no longer uses the static SERVERS / ACCESS maps: FtbQuestRuntime holds the unified queries, knowledge index and notification state; ModuleContext.sharedRuntime shares an instance within one installation, and ModuleManager deduplicates validate / tick / close by object identity and handles resource closing when installation fails. Player sessions are counted per configuration, and the player reference is cleared only when the last one closes.

Later syncs must change FtbQuestAdapter.runtime's ModuleContext parameter, the QuestSystemModule reflection signature, the explicitly submitted instance notification calls and the runtime lookup of `/system ftb reload` together. FTB notifications become instance `@SubscribeEvent` listeners that are registered on install and unregistered on close; the old version adjusts them to the actual event API, keeps optional dependencies isolated and does not go back to a server-keyed Map. Currently only master is changed and 1.21.1 has not been synced; the compilation result does not mean runtime events and world-save switching have been accepted.

In the same round ModuleContext keeps AgentEngine / the module registry as fixed fields read through engine() / modules(), and other service injection moves to `ContextType<T>` keys and a Map. AssistantServer uses a two-argument constructor plus chained put; FTB and other modules use fixed getters or `context.get(ContextTypes.XXX)` according to their dependencies. ModuleManager publishes ModuleContextEvent before actual assembly so other mods can inject extension services synchronously. When porting, sync ContextType / ContextTypes, the event and the call sites together, keep the original sharedRuntime installation scope and lifecycle, and do not restore the old constructor that adds a field per service.
